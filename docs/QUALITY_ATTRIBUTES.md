# 1.3.0 质量属性与场景

## 1. 可修改性

**场景：新增“颈围”指标。**

期望：通过 `body_metric_defs` 增加定义即可进入选择列表，不修改身体记录页面结构。

**场景：增加新的运动消耗算法。**

期望：替换/新增 Domain Calculator，不改页面和数据库访问层。

**场景：增加一种日志类型。**

期望：扩展 Note Domain/常量即可复用同一 `notes + attachments` 模型，不新建一套页面和数据库。

## 2. 可用性 / 易用性

- 首页 5 秒内可以看见今日计划、营养和热量状态。
- 身体、学习、训练完成后可就地进入相关笔记，不需要重新寻找关联记录。
- 笔记支持相机、相册和自动草稿恢复。
- 错误提示使用业务语言，不直接暴露云 SDK 错误。
- 诊断页可复制版本和环境，降低排错成本。

## 3. 可靠性

- 关键写操作有防重复设计或业务唯一语义。
- Notes 使用 `clientMutationId` 支持网络失败后幂等重试。
- 删除 Note 先标记业务删除，再清附件；附件清理失败不阻断业务结果。
- 提醒使用确定性消息 ID；同一用户、计划和日期只生成一条站内消息。
- 推送前重新检查当天打卡及每周计划进度，降低过期提醒概率。
- 审计日志失败不能影响主业务。
- Schema 不满足当前版本时 API 拒绝继续执行，避免新代码操作旧结构。

## 4. 安全与隐私

- 跨用户访问只允许服务端判断。
- Notes 当前只允许 owner 读取和修改。
- 群组只能突破“计划执行状态”的好友隐私，不能读取身体、饮食、日志和照片。
- 云日志不打印用户的体重、饮食、笔记正文或照片内容。
- `admin-init` 初始化后应停用/删除，或配置初始化 Token。

## 5. 性能

- Dashboard 并行读取身体、计划、营养、运动、学习摘要。
- Notes 列表默认 20 条分页，附件按一批 noteId 获取，避免逐条查询附件。
- 趋势报告批量并行读取区间数据，不按日期逐日查询；7/30/90 天共用同一聚合 Domain。
- 群组成员完成率当前适用于小群组；若群组扩大到几十人，计划引入 `group_daily_stats` 聚合表。

## 6. 可测试性

Domain 层禁止直接依赖数据库：

- Nutrition
- Plan Schedule
- Exercise Calories
- Note Rules

这些规则均可通过 Node 原生测试运行。

## 7. 可运维性

- 每个 API 有 requestId、action、耗时和错误码。
- 客户端控制台打印 action/code/requestId，不打印敏感 payload。
- `about` 页面展示版本、Schema 和环境。
- `npm run verify` 是发版前质量门禁。
